## 三、号码规范化

一个函数、一处定义，入站匹配、联系人新建 / 编辑 / 表格导入、存量迁移都用它：

每一步都作用在上一步得到的数字串上（不看原文）：

1. 去掉数字以外的所有字符（`+`、空格、横线、括号、点号都去掉）。
2. 以 `00` 开头（国际拨号前缀）：去掉这两个 0。
3. 以 `0` 开头（马来西亚本地写法）：把这个 `0` 换成 `60`。
4. 以 `600` 开头（国家码后面又写了本地的 0，如 `+60 012-345 6789`）：去掉 `60` 后面紧跟的所有 `0`。
5. 结果 8–15 位才算有效号码；否则视为无法规范化：入站不会出现（Meta 给的就是 E.164 数字），
   手工录入的原样保存、不参与匹配，存量迁移里原样保留。

规则是幂等的：对有效结果再规范化一次得到同一个值（结果不以 `0` 开头，也不以 `600` 开头）。

| 原文 | 结果 |
|---|---|
| `+60 12-345 6789` | `60123456789` |
| `012-3456789` | `60123456789` |
| `0060123456789` | `60123456789` |
| `+0060123456789` | `60123456789` |
| `+60 012-345 6789` | `60123456789` |
| `60123456789` | `60123456789` |
| `+65 9123 4567` | `6591234567` |
| `12345`、空白、`--` | 无效，原样 |

已知局限：不带国家码、也不以 0 开头的外国本地号码（如新加坡 `91234567`）会原样当作有效号码，不补国家码。

存储形状：纯数字、不带 `+`（例如 `60123456789`）。页面上显示的就是这个形状，接受。

**号码冲突不存字段**：规范化之后同号码的联系人可以直接查出来，联系人接口按查询结果返回 `phone_conflict`，
管理员改掉号码或删除重复联系人后自然消失，不存在「标记忘了清」。只有号码本身已是有效规范化形式的联系人才查
（未删除、号码相同、多于一个）；无效的原样号码不参与匹配，也不算冲突。

## 四、接口

`POST /internal/chatbot/events`，只在共享 Docker 网络内可达，不经 nginx 暴露。一次请求一个事件。

### 鉴权

- 请求头 `X-Acuven-Timestamp`（Unix 秒）与 `X-Acuven-Signature: sha256=<hex>`，
  签名 = HMAC-SHA256(密钥, `<timestamp>.<原始请求体字节>`)。
- 时间戳与 CRM 当前时间相差超过 300 秒拒绝。
- CRM 配置 `CHATBOT_EVENTS_SECRET` 与可选的 `CHATBOT_EVENTS_SECRET_PREVIOUS`，任一把验过即可（轮换用）；常数时间比较。
- 只用于这一个方向；第 2 阶段 CRM → chatbot 用另一把。不复用现有明文比对的 `X-Internal-Secret`。

### 请求体（公共部分）

```json
{
  "event_id": "chatbot 生成的 UUID，只用于日志与排查，CRM 不存",
  "type": "customer_message | ai_reply | console_reply | handover_changed | delivery_status",
  "occurred_at": "2026-10-12T08:00:00Z",
  "visitor": {
    "phone": "60123456789 或 null",
    "bsuid": "MY.xxxx 或 null",
    "profile_name": "WhatsApp 资料名，或 null"
  }
}
```

`phone` 与 `bsuid` 至少一个非空。`profile_name` 只在新建联系人时用作名字，不覆盖已有联系人的名字；超过 100 字符截断到 100。

**`occurred_at`** 是 chatbot 一侧事件发生的时刻（消息类取 Meta 时间戳或 chatbot 发出的时刻，接管类取状态改变的时刻），
必须带时区、**精确到微秒**，且不得晚于 CRM 当前时间 300 秒以上（否则 422）。消息入库时用它作 `created_at`（换算成 UTC），
死信补投的消息因此仍按真实时间排在会话里。

### 各类型的附加字段

| type | 附加字段 | CRM 怎么处理 |
|---|---|---|
| `customer_message` | `message: {wa_message_id, body}` | 入站消息，`author_kind=customer`，未读 |
| `ai_reply` | `message: {wa_message_id, body}`、`bot_id` | 出站消息，`author_kind=ai`，记 `bot_id`，已读 |
| `console_reply` | `message: {wa_message_id, body}` | 出站消息，`author_kind=console`，已读（控制台只有一个口令，没有坐席身份） |
| `handover_changed` | `handover: {active, expires_at}` | 更新联系人的接管状态 |
| `delivery_status` | `status: {wa_message_id, status, error_code, error_title}` | 更新那条消息的送达状态 |

`body` 是文字正文；媒体由 chatbot 转成占位文字（如 `[image] 说明`），第 1 阶段不传媒体本身。

**字段校验**（任一不满足返回 422，不入库）：

| 字段 | 规则 |
|---|---|
| `event_id` | 非空字符串，最长 64 |
| `visitor.phone` | 可空；非空时 8–15 位纯数字 |
| `visitor.bsuid` | 可空；非空时最长 140 |
| `message.wa_message_id`、`status.wa_message_id` | 非空，最长 200 |
| `message.body` | 非空字符串 |
| `bot_id` | `ai_reply` 必填，非空，最长 50；其他类型不得出现 |
| `handover.active` | 布尔，必填 |
| `handover.expires_at` | `active` 为 true 时必填、带时区；为 false 时必须为 null |
| `status.status` | 只接受 `sent`、`delivered`、`read`、`failed` |
| `status.error_code`、`status.error_title` | 可空 |

请求体里未列出的字段忽略（chatbot 以后加字段不会让旧 CRM 拒收）。

### 返回

| 情况 | 状态码 | chatbot 怎么办 |
|---|---|---|
| 已存、重复（同一 `wa_message_id`）、或按规则忽略（见下） | 200，`{"result": "stored" \| "duplicate" \| "ignored"}` | 出队 |
| 请求体不合法 | 422 | 进死信，不重试 |
| 签名或时间戳不对 | 401 | 退避重试并告警（多半是密钥或时钟配错，修好后事件不丢） |
| CRM 未配置密钥 | 503 | 退避重试 |
| 其他服务端错误 | 5xx | 退避重试 |

chatbot 按顺序投递：队首没成功之前不发后面的，保证同一访客的事件先后不乱。

## 五、CRM 的处理规则

### 找联系人

1. 有 `phone`：按号码找未删除的联系人；多于一个取最早创建的，`created_at` 相同再按 `id` 字典序取最小（P2，结果确定）。
   找到且事件带 `bsuid`、该联系人还没有、也没有别的**未删除**联系人占用这个 `bsuid`：补上（被已删除联系人占用时按下面「BSUID 让位」处理）。
2. 按号码没找到、但带 `bsuid`：按 `bsuid` 找**未删除**的联系人；找到且它还没有号码，补上号码（访客后来公开了号码）。
3. 都没找到：新建联系人。名字取 `profile_name`，没有就取号码，再没有取 `bsuid`；`is_gateway=false`（P4）；
   调 `assign_contact()` 指派；建 lead 商机。与现有入站逻辑一致。

**BSUID 让位**：`whatsapp_bsuid` 是全表唯一（含已删除行）。要把某个 `bsuid` 写到未删除联系人上、而它被一个已删除联系人占着时，
先把已删除联系人的 `whatsapp_bsuid` 清空，再写上。已删除联系人不参与匹配，也不能挡住新联系人。

例：联系人 A（`bsuid=MY.1`）已被删除；访客只带 `bsuid=MY.1` 来消息 → 第 2 步找不到未删除的 → 第 3 步新建 B，
A 的 `bsuid` 清空、B 的 `bsuid=MY.1`；下一条同一访客的消息按第 2 步找到 B。

消息类事件都会走这一步（AI 回复或控制台回复先于顾客消息到达时也一样建联系人，正常顺序下不会发生）。
`handover_changed` 与 `delivery_status` 找不到联系人或消息时返回 `ignored`，不新建。

### 消息

- 按 `wa_message_id` 去重（沿用 `messages.external_id` 唯一键），重复返回 `duplicate`。
- 消息的 `assigned_to` 取联系人当前负责人，与现有入站一致；转派时随联系人一起转（任务二 2.1 已做）。
- 收件人 / 发件人字段：访客一侧填号码（没有号码填 `bsuid`），chatbot 一侧填固定值 `ai_chatbot_demo`。

### 接管状态

- 联系人存三项：是否接管中、到期时间、最后一次更新所依据的事件时间（精确到微秒）。
- 事件的 `occurred_at` **早于或等于**已存的更新时间就忽略，返回 `ignored`（死信补投的旧事件、同一事件重复投递，都不能把新状态盖掉）。
  `occurred_at` 精确到微秒，所以真实的先后两次变化不会撞在同一时刻；接口拒收未来超过 300 秒的时间，
  一条时间写错的事件因此不会把以后的真实事件全挡掉。
- `active` 为 false 时到期时间存空。

例：已存「接管中，到期 10-13 08:00，更新于 10-12 08:00:00.250000」。
收到 `occurred_at=10-12 08:00:00.100000` 的「结束接管」→ 早于已存 → 忽略，仍是接管中。
收到 `occurred_at=10-12 08:00:00.250000` 的同一事件重投 → 等于已存 → 忽略。
收到 `occurred_at=10-12 09:30:00.000001`、`active=false` → 晚于已存 → 写入：未接管、到期时间空、更新于 09:30:00.000001。
- chatbot 在开始接管、每次续期、结束接管（顾客发 menu、控制台交还、空闲到期）时都推一次。
  CRM 显示时以到期时间为准：标着接管中但已过期，按「AI 在回」显示，不依赖 chatbot 补推到期事件。

### 送达状态

- 只更新 `external_id` 等于 `wa_message_id` 的**出站**消息；找不到、或那条是入站消息，返回 `ignored`。
- 状态排成一条线：空 < `sent` < `delivered` < `failed` < `read`。新状态比已存的高才写入，相等或更低返回 `ignored`。
  所以 `failed` 能盖掉 `sent`、`delivered`；`read` 能盖掉 `failed`（Meta 说已读，就是收到了），这时清空失败原因；
  `failed` 之后来的 `delivered` 被忽略。
- 写入 `failed` 时，失败原因 = `<error_code>: <error_title>`；只有其中一个就只写那一个；两个都空写 `failed`；截断到 300 字符。
  收件箱显示「未送达」及原因。

例：消息 M 已存 `delivered`。收到 `failed`（131047，Re-engagement message）→ 写入 `failed`，原因 `131047: Re-engagement message`。
再收到 `delivered` → 低于 `failed` → 忽略。再收到 `read` → 写入 `read`，原因清空。

### 修订一（2026-10-12，设计预审发现，待 Kelvin 批准）

登记 CRM-TASK-006 至 009 前跑设计预审，四个都是 NOT_READY。成立的发现与改法：

| 发现 | 改法 | 节 |
|---|---|---|

| 资料名超过 `contacts.name` 的 100 字符 | 截断到 100 | 四 |
| 已删除联系人仍占着唯一的 BSUID，新联系人写不进去，5xx 卡住队列 | BSUID 让位：清掉已删除联系人上的 BSUID | 五 |
| 「最早创建」没有平局规则，MySQL 时间精确到秒 | 再按 `id` 取最小 | 五 |
| `failed` 之后能否变成别的状态、相等状态、入站消息的状态、错误码与标题怎么拼没写 | 一条线排序、只升不降，`read` 可盖 `failed`；只更新出站消息；写明拼法 | 五 |

`ai_reply` 以外不带 `bot_id`。
